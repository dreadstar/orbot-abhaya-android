# Output Format — Collected File Document Structure

Reference for Phase 3 of the Raptor Mini Executor skill.
Read this before appending any file to the output document.

---

## Overall Document Structure

The output `.md` file has four parts, written in this order:

```
Part 1 — Document Header     (written in Phase 1)
Part 2 — Collected Files     (appended incrementally in Phase 3)
Part 3 — Collection Summary  (written in Phase 4)
```

Nothing may be appended after Part 3.

---

## Part 1 — Document Header

Written once during Phase 1, before any source file is read.

```markdown
# [OUTPUT_FILE basename — no extension, underscores to spaces]

## SESSION METADATA
Generated by   : Raptor Mini Executor
Prompt source  : [first 60 characters of INVESTIGATION FOCUS, truncated with …]
Files planned  : [N — total items in COLLECT_LIST]
Files collected: 0

---

## CONFIRMED EVIDENCE (from prompt)

[CONFIRMED EVIDENCE block — pasted verbatim from the prompt]

---

## INVESTIGATION FOCUS (from prompt)

[INVESTIGATION FOCUS block — pasted verbatim from the prompt]

---

## COLLECTED FILES

```

The `Files collected: 0` counter line must be updated after each successful
collection in Phase 3. Overwrite that line with the current count.

The `## COLLECTED FILES` header is the insertion point for all Phase 3 content.

---

## Part 2 — File Block Format

For each successfully collected file, append one block in this exact format:

````markdown
### [ClassName.kt] — [absolute/path/to/ClassName.kt]

```[language_tag]
[verbatim file contents — no changes of any kind]
```

---
````

**Language tag mapping:**

| Extension | Tag |
|---|---|
| `.kt` | `kotlin` |
| `.java` | `java` |
| `.xml` | `xml` |
| `.gradle` | `groovy` |
| `.gradle.kts` | `kotlin` |
| `.json` | `json` |
| `.yaml` / `.yml` | `yaml` |
| `.properties` | `properties` |
| `.toml` | `toml` |
| anything else | (no tag — just triple backticks) |

**Rules for file block content:**

- Copy file contents byte-for-byte. No modifications.
- Do not add line numbers.
- Do not add comments like `// relevant section below`.
- Do not trim leading or trailing blank lines from the file.
- Do not replace any content with `...` or `[omitted]`.
- If the file is empty, write `(empty file)` inside the code block.

**Rules for the block header line:**
- Use the basename of the file (not the full path) as the display name.
- Include the full absolute path after the em-dash.
- Example: `### PaymentProcessor.kt — /home/user/project/data/payment/PaymentProcessor.kt`

**Separator:**
Always append `---` on its own line after the closing triple backtick.
This separates file blocks visually and makes the document parseable.

## MISSING Entry Format

For each file that could not be found after all four search strategies:

```markdown
### [item name from COLLECT list] — MISSING

**Status:** NOT FOUND
**Searched with:**
- [query 1] via [strategy]
- [query 2] via [strategy]
- [query 3] via [strategy]

---
```

Log every search attempt. This allows Claude to diagnose the failure in the
next session and provide better search terms.

---

## SKIPPED Entry Format

For each file skipped due to the DO NOT RE-COLLECT list:

```markdown
### [item name] — SKIPPED (DO NOT RE-COLLECT)

---
```

One line is sufficient. No search information needed.

---

## Part 3 — Collection Summary

Written once, at the end of Phase 4, after all files are processed.

```markdown
## COLLECTION SUMMARY

| Item | Status | Path |
|---|---|---|
| [name] | COLLECTED | [absolute path] |
| [name] | MISSING | — |
| [name] | SKIPPED | — |

Files collected : [N]
Files missing   : [M]
Files skipped   : [K]
Total planned   : [N + M + K]

COLLECTION COMPLETE. No analysis. No summaries. No commentary.
```

After this block, nothing further is written to the output file.

---

## Counter Update Protocol

The `Files collected: 0` line in the document header must stay accurate.
After each successful Phase 3 collection, update it:

1. Locate the line: `Files collected: [current count]`
2. Replace with: `Files collected: [current count + 1]`

This can be done with a targeted string replacement. The line appears exactly
once in the document (in the SESSION METADATA block).

If the tool does not support in-place line replacement, update the counter
in the Phase 4 summary only — do not leave the document in an inconsistent
state by attempting a partial update.

## Worked Example

Suppose `COLLECT_LIST` has three items:
- `PaymentProcessor.kt` — found at `/project/data/payment/PaymentProcessor.kt`
- `RouteManager.kt` — in SKIP_LIST
- `GatewayConfig.kt` — not found after all strategies

The output file would contain, in order:

```
Part 1 header (with metadata, confirmed evidence, investigation focus)

## COLLECTED FILES

### PaymentProcessor.kt — /project/data/payment/PaymentProcessor.kt

```kotlin
[full contents of PaymentProcessor.kt]
```

---

### RouteManager.kt — SKIPPED (DO NOT RE-COLLECT)

---

### GatewayConfig.kt — MISSING

**Status:** NOT FOUND
**Searched with:**
- "GatewayConfig.kt" via Strategy 2A (workspace filename search)
- "class GatewayConfig" via Strategy 2B (workspace class search)
- find . -name "GatewayConfig.kt" via Strategy 3 (filesystem search)
- "class GatewayCfg" via Strategy 4C (abbreviation variant)

---

## COLLECTION SUMMARY

| Item | Status | Path |
|---|---|---|
| PaymentProcessor.kt | COLLECTED | /project/data/payment/PaymentProcessor.kt |
| RouteManager.kt | SKIPPED | — |
| GatewayConfig.kt | MISSING | — |

Files collected : 1
Files missing   : 1
Files skipped   : 1
Total planned   : 3

COLLECTION COMPLETE. No analysis. No summaries. No commentary.
```
