# MESH JOIN PLAN - PART 1: EXECUTIVE SUMMARY & ARCHITECTURE

## Executive Summary

This plan details the implementation of **mesh-wide discovery QR joining** for Orbot's Meshrabiya mesh networking system. The implementation uses QR codes containing shared mesh credentials that enable devices to discover and connect to ANY available mesh hotspot, providing resilient joining that survives hotspot changes.

### Key Innovation: Mesh-Wide Discovery

**Traditional WiFi QR Limitation:** Encodes a single SSID → if that hotspot goes down, QR code becomes useless.

**Our Solution:** Encode shared password + SSID pattern → device scans for ANY matching hotspot → automatic failover if initial hotspot fails.

### Key Findings

✅ **DISCONNECTED devices CAN join mesh** - No connection state preconditions exist

### User Questions Answered

**Q1: "Can DISCONNECTED devices use Join Mesh functionality?"**

**A: YES** - The code has no restrictions preventing DISCONNECTED devices from joining. The `connectAsStation()` method in AndroidVirtualNode (Line 155-159) and `connectToHotspot()` in MeshrabiyaWifiManagerAndroid (Lines 422-435) have NO connection state preconditions. Android's ConnectivityManager handles all state transitions automatically.

**Q2: "Do all hotspot devices in the mesh share the same SSID and password?"**

**A: NO for individual SSIDs, YES for shared password - but QR joining uses MESH-WIDE DISCOVERY**

**SSID Architecture:**
- **Android 13+ (API 33+):** SSID = `meshr-<node_virtual_address_hex>`
  - Example: Node `169.254.45.142` → SSID `meshr-a9fe2d8e`
  - Each device has **UNIQUE SSID** based on its virtual address
  - Source: LocalOnlyHotspotManager.kt Lines 118-119

- **Android 8-12 (API 26-32):** SSID is **randomly generated by Android**
  - Format: `AndroidShare_XXXX` (e.g., `AndroidShare_4908`)
  - App has NO control over generation
  - Random per hotspot creation, not persistent

**Password Architecture:**
- **Android 13+:** Hardcoded `"meshtest12"` for ALL devices
  - Source: LocalOnlyHotspotManager.kt Line 119
  - Shared across entire mesh for simplified onboarding

- **Android 8-12:** Randomly generated by Android
  - App has NO control
  - Must be retrieved from callback and shared via QR

**Architectural Reason for Unique SSIDs:**
The SSID encodes the device's virtual address, which is essential for:
1. **Mesh routing** - Neighbors map SSID → virtual address → routing table
2. **Connection persistence** - BSSID lookups use SSID as key
3. **Topology discovery** - Originating messages include virtual address

**QR Code Joining Strategy: MESH-WIDE DISCOVERY**

Instead of encoding a single device's SSID, the QR code contains:
- **Shared mesh password**: `"meshtest12"` (for Android 13+)
- **SSID pattern**: `"meshr-*"` (matches any mesh hotspot)
- **Optional**: Bootstrap SSID list (known available hotspots)

**Joining Process:**
1. Device B scans QR code from any mesh device
2. Device B performs WiFi scan for all SSIDs matching `"meshr-*"`
3. Device B connects to strongest/closest available hotspot
4. Device B discovers full mesh topology via originating messages (within 3 seconds)
5. **If initial hotspot fails**, Device B automatically rescans and connects to next available hotspot
6. **No need to rescan QR codes** - Device B remembers the shared password

**Benefits:**
- ✅ QR code works even if the device that generated it goes offline
- ✅ Automatic failover to other hotspots without user intervention
- ✅ Resilient to dynamic mesh topology changes
- ✅ Single QR code provides access to entire mesh, not just one device

**Q3: "What if the initial hotspot goes down after joining?"**

**A: Automatic recovery** - Device maintains the shared password and automatically:

1. **Detects disconnection** via connection state monitoring
2. **Rescans for mesh hotspots** (all SSIDs matching `"meshr-*"`)
3. **Reconnects to strongest available** hotspot using same password
4. **Rejoins mesh topology** via originating message broadcasts
5. **No user intervention required** - seamless failover

**Q4: "Can devices switch between hotspot and station modes?"**

**A: YES for Android 13+ (concurrent AP+STA), COMPLEX for Android <13**

**Feasibility Analysis:**

**Scenario 1: Concurrent AP+STA (Android 13+, most modern devices)**
```kotlin
// Device can be BOTH hotspot and station simultaneously
// No switching needed - maintains both roles
setWifiHotspotEnabled(true)   // Creates hotspot
connectAsStation(config)       // Joins another hotspot
// Both remain active - mesh state preserved
```

**Scenario 2: Non-Concurrent (Android <13, older devices)**
```kotlin
// Must choose: hotspot OR station (not both)
// Switching requires coordination:

// Become hotspot from station:
meshrabiyaWifiManager.stopStation()        // Drops current connection
delay(1000)                                 // Brief pause
meshrabiyaWifiManager.startHotspot()       // Creates hotspot
// Brief service disruption - neighbors lost during transition

// Return to station from hotspot:
meshrabiyaWifiManager.stopHotspot()        // Stops hotspot  
delay(1000)                                 // Brief pause
meshrabiyaWifiManager.connectToHotspot()   // Rejoins network
// Clients connected to this hotspot are now stranded
```

**Current State:** No automatic switching logic exists. Devices remain in their chosen mode until manually changed.

```kotlin
    .getConstructor()
    .newInstance()

    .invoke(configBuilder, "meshr-${localNodeAddr.encodeAsHex()}")

// Set preferred band (5GHz if requested)

    configBuilder::class.java.getMethod("setBand", Int::class.javaPrimitiveType)
        .invoke(configBuilder, BAND_5GHZ or BAND_2GHZ)

// Build final configuration
val softApConfig = configBuilder::class.java.getMethod("build").invoke(configBuilder)

// Start LocalOnlyHotspot with custom config

    "startLocalOnlyHotspot",
    softApConfig::class.java,
    Executor::class.java,
    WifiManager.LocalOnlyHotspotCallback::class.java
).invoke(wifiManager, softApConfig, executor, localOnlyHotspotCallback)
```

- SSID format: `meshr-` + 8-character hex encoding of virtual address
- Virtual address is a 32-bit integer assigned to each VirtualNode
- Password: Hardcoded `"meshtest12"` (could be made configurable)
- BSSID: Random MAC generated once, persisted in DataStore for stability
- Band: Configurable (2.4GHz, 5GHz, or dual-band)

### 2. Connection State Requirements Analysis

#### Why the Confusion About CONNECTED/CONNECTING?

The research agent initially suggested requiring mesh to be CONNECTED/CONNECTING before allowing "Join Mesh" because:

1. **UI/UX consideration** - Button placement in "expanding pane" that should only be enabled when mesh is active
2. **Misinterpretation of concurrent AP+STA** - Thought concurrent support was needed for joining (it's not)

**Reality:** The restriction was a UI design choice, NOT a technical requirement.

**Usage 2: MESH_ROUTER Role Assignment**

**File:** `Meshrabiya/lib-meshrabiya/src/main/java/com/ustadmobile/meshrabiya/vnet/EmergentRoleManager.kt`

**Lines 329-338:** (VERIFIED)
```kotlin
// Router roles - requires centrality AND concurrent AP+STA support
val centralityResult = calculateBFSCentrality()
if (fitness > 0.6 && centralityResult.centralityScore > centralityThreshold
    && concurrentApStationSupported) {  // ← CRITICAL: Need concurrent for routing
    roles.add(MeshRole.MESH_ROUTER)
}
```

**What This Means:**
- **Concurrent = TRUE:** Can run hotspot AND be connected as station simultaneously
  - Enables MESH_ROUTER role (can forward traffic between networks)
  - Uses LocalOnlyHotspot (persistent, survives restarts)
  - Ideal for mesh bridges and gateways

- **Concurrent = FALSE:** Must choose hotspot OR station
  - Cannot get MESH_ROUTER role (no traffic forwarding)
  - Uses WiFi Direct Group (session-based)
  - Switching modes requires disconnection

**Joining as Station Does NOT Require Concurrent Support:**
Any device can join as a station, regardless of concurrent capability. The limitation only affects:
1. Whether it can ALSO run a hotspot while connected
2. Whether it qualifies for MESH_ROUTER role

## Summary of Key Insights

### SSID/Password Architecture
- ✅ Each device has **unique SSID** (encodes virtual address)
- ✅ All Android 13+ devices share **same password** (`"meshtest12"`)
- ✅ Android 8-12 devices have **random credentials** (Android-generated)
- ✅ BSSID (MAC) is **persistent** per device (stored in DataStore)

### Connection Requirements
- ✅ DISCONNECTED devices **CAN join** mesh (no preconditions)
- ✅ Joining **does NOT require** concurrent AP/STA support
- ✅ Concurrent support **only affects** MESH_ROUTER role eligibility

### Mesh Discovery
- ✅ Devices discover each other via **broadcast originating messages** (every 3 seconds)
- ✅ Topology map contains **all reachable nodes** (not just 1-hop neighbors)
- ✅ Joining any hotspot provides **access to entire mesh** (via topology discovery)
